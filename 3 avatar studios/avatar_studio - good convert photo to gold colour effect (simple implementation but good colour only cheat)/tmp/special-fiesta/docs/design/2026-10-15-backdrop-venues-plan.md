## 1. What exists today

### 1.1 Three rendering styles, one venue

The three "backdrops" are not three parallel scenes — they are three **rendering styles**
applied to the same venue (Sentosa):

| Style name | Resolution | Assets | Art module | Generator |
|---|---|---|---|---|
| `classic` | 1 px per art unit | `public/scene/*.png` | `lib/sceneArt.ts` (SCENE_PARTS) | `scripts/generate-scene.mjs` + `scene-art.mjs` + `scene-sprites.mjs` |
| `fine` | 2 px per art unit | `public/scene-2x/*.png` | `lib/sceneArt.ts` (SCENE_PARTS_FINE) | same generator, `scale=2` |
| `real` | photoreal | `public/scene-real/*.png` + `.jpg` | `lib/sceneArtReal.ts` | `scripts/generate-real-scene.mjs` + `real-scene-geometry.mjs` |

All three are Sentosa. The goal of this plan is to make "venue" orthogonal to
"style" so a future event at another location can produce its own classic, fine and
real backdrops without touching Sentosa's.

### 1.2 The avatar backdrop is a different feature

`BackdropStyleRow.tsx`, `AvatarStudio.tsx`, `lib/avatar/backdropPreview.ts`, and
`AVATAR_BACKDROP_SWATCHES` are about the **coloured pattern behind a participant's
portrait photo** (sunburst, concentric rings, waves, psychedelic swirls). These use
the word "backdrop" but they are a persona-customisation feature that has nothing to
do with the beach scene. They are not touched by this plan.

## 2. Where Sentosa-specific content is hard-coded

### 2.1 Generated art modules (ts files written by the generators)

**`apps/web/src/lib/sceneArt.ts`** (generated by `generate-scene.mjs`)
- Exports `SCENE_PARTS` and `SCENE_PARTS_FINE` — object shapes keyed by Sentosa layer

  `player1`–`player4`, `ball`, `clouds`, `waves`, `foam`.

- All `src` URLs hard-point at `/scene-real/`.
- Rosters `REAL_PLAYERS_FAR`, `REAL_PLAYERS_NEAR`, `REAL_CABLECARS`, `REAL_BOATS`,
  `REAL_MOORED` are Sentosa-specific groupings.

### 2.2 CSS design tokens

**`apps/web/src/styles/tokens.css`** (line 5–21)
- Comment literally says `/* Sentosa palette */`.
- Variables `--sea-deep`, `--sea`, `--sea-light`, `--sky`, `--sand`, `--sand-deep`,
  `--palm`, `--gold`, `--merlion` are Sentosa-derived colour names.
- `--scene-sky: #5fb8ec` is annotated as "top row of the backdrop panorama (ADR-022):

### 2.6 How backdrop selection works today

`lib/scene/backdropChoice.ts` owns `psd.backdrop.v1` (localStorage, ADR-019).

1. URL param `?backdrop=classic|fine|real` is the deliberate switch.
2. `classic` and `fine` are "sticky": written to storage and remembered across navigation.
3. `real` is deliberately NOT sticky (18 MB of photographs — ADR-201).
4. Default (no param, nothing stored) is `classic`.

`BackdropChoice = 'classic' | 'fine' | 'real'` — no venue dimension exists.

`BeachScene.tsx` calls `resolveBackdrop(useLocation().search)` on every render and
dispatches to `RealBeachScene` if `real`; otherwise it picks `SCENE_PARTS` vs
`SCENE_PARTS_FINE` from the Sentosa art module. `GameboyShell.tsx` imports and renders
`BeachScene` directly (lines 4 + 193).

## 3. Proposed venue architecture

### 3.1 Core concept

Style (`classic` / `fine` / `real`) and venue (`sentosa` / `east-coast` / …) are
orthogonal. A venue supplies art, geometry and colour tokens for its location; a style
picks the rendering mode (pixel 1×, pixel 2×, photoreal). Not every venue needs all
three styles — a new venue might start with only `classic`.

### 3.2 `VenueDefinition` type

New file: `apps/web/src/lib/scene/venueTypes.ts`

```typescript
export type VenueId = string;
export type StyleKind = 'classic' | 'fine' | 'real';

/**
 * Colour overrides the participant shell applies when this venue is active.
 * These are CSS custom property values, keyed by the token name (no '--' prefix).
 */
export interface VenueTokens {
  'scene-sky': string;    // top row of the panorama; shell background matches it
  'sea-deep': string;
  'sea': string;
  'sea-light': string;
  'sky': string;
  'sand': string;
  'sand-deep': string;
}

/**
 * The pixel art for a venue's classic and fine styles.
 * These are the same shape as SCENE_PARTS / SCENE_PARTS_FINE.
 * The generator produces them; they live in the venue's art module.
 */
export interface PixelVenueArt {
  readonly parts1x: SceneParts;
  readonly parts2x: SceneParts;
  readonly playerPeriods: readonly string[];
  readonly version: string;
}

/**
 * The photoreal art for a venue's real style.
 * Same shape as SCENE_PARTS_REAL and its rosters.
 */
export interface RealVenueArt {
  readonly parts: RealSceneParts;
  readonly playersFar: readonly RealScenePart[];
  readonly playersNear: readonly RealScenePart[];
  readonly cablecars: readonly RealScenePart[];
  readonly boats: readonly RealScenePart[];
  readonly moored: readonly RealScenePart[];
  readonly playerPeriods: readonly string[];
  readonly version: string;
}

export interface VenueDefinition {
  readonly id: VenueId;
  readonly name: string;
  readonly styles: readonly StyleKind[];   // which styles are available
  readonly pixel: PixelVenueArt | null;
  readonly real: RealVenueArt | null;
  readonly tokens: VenueTokens;
}
```

(`SceneParts` and `RealSceneParts` are the existing shapes inlined from `sceneArt.ts`
and `sceneArtReal.ts`; they become shared types rather than implied by the `as const`
exports.)

### 3.3 Venue registry

New file: `apps/web/src/lib/scene/venueRegistry.ts`

```typescript
import type { VenueDefinition, VenueId } from './venueTypes.js';
import { SENTOSA_VENUE } from './venues/sentosa/definition.js';

const REGISTRY: ReadonlyMap<VenueId, VenueDefinition> = new Map([
  ['sentosa', SENTOSA_VENUE],
]);

export const DEFAULT_VENUE_ID: VenueId = 'sentosa';

export function getVenue(id: VenueId): VenueDefinition {
  return REGISTRY.get(id) ?? REGISTRY.get(DEFAULT_VENUE_ID)!;
}

export function listVenues(): readonly VenueDefinition[] {
  return [...REGISTRY.values()];
}
```

### 3.5 Asset folder convention

```
apps/web/public/
  venues/
    sentosa/
      pixel/          ← was public/scene/
        panorama.png
        clouds.png
        … (14 layers)
      pixel-2x/       ← was public/scene-2x/
        … (same 14 layers at 2×)
      real/           ← was public/scene-real/
        panorama.jpg
        … (30+ layers)
    east-coast/       ← future venue
      pixel/
      real/
```

Old paths (`/scene/`, `/scene-2x/`, `/scene-real/`) are served as redirects during
Stage 1 (or via a Vite alias) until the art modules are regenerated with the new paths.
The art module generators always write absolute `/venues/<id>/pixel/` paths.

### 3.6 Generator convention

```
apps/web/scripts/
  venues/
    sentosa/
      generate-pixel.mjs    ← moved from scripts/generate-scene.mjs (+ scene-art.mjs + scene-sprites.mjs)
      generate-real.mjs     ← moved from scripts/generate-real-scene.mjs (+ real-scene-geometry.mjs)
  generate-scene.mjs        ← thin wrapper: `node scripts/venues/sentosa/generate-pixel.mjs`
  generate-real-scene.mjs   ← thin wrapper: `node scripts/venues/sentosa/generate-real.mjs`
```

The wrappers keep the existing `npm run scene` invocation working throughout migration.
A venue author runs `node scripts/venues/<id>/generate-pixel.mjs` to (re)build their
venue's pixel art and update their venue's art module.

### 3.7 Venue selection — event-level config, not per-user

The `classic`/`fine`/`real` style choice is per-user and stored in localStorage
(`psd.backdrop.v1`, per ADR-201 asymmetry). The **venue** is an event-level decision
made by the superadmin and distributed to every participant the same way other event
config is (the existing `/api/config` or equivalent endpoint).

In practice: `psd.venue.v1` is written to localStorage by the participant shell after
reading it from the server config. Participants do not individually choose their venue;
the superadmin's choice propagates. The `?backdrop=` URL param continues to control
style only.

`backdropChoice.ts` changes shape:

```typescript
export type SceneChoice = { venue: VenueId; style: BackdropStyle };

export function resolveScene(search: string): SceneChoice {
  const style = resolveBackdrop(search);  // unchanged today
  const venue = readItem(VENUE_KEY) ?? DEFAULT_VENUE_ID;
  return { venue: isKnownVenue(venue) ? venue : DEFAULT_VENUE_ID, style };
}
```

### 3.8 Component refactor

`BeachScene.tsx` becomes venue-aware:

```tsx
export function BeachScene() {
  const { venue, style } = resolveScene(useLocation().search);
  const venueDefinition = getVenue(venue);
  if (style === 'real') return <RealBeachScene venue={venueDefinition} />;
  const parts = style === 'fine' ? venueDefinition.pixel!.parts2x
                                 : venueDefinition.pixel!.parts1x;
  // … rest unchanged
}
```

`RealBeachScene.tsx` receives `VenueDefinition` as a prop instead of importing the
Sentosa art module directly.

### 3.9 CSS token injection

Rather than hardcoding Sentosa token values in `tokens.css`, the shell injects the
active venue's token overrides as inline CSS variables on `<body>` or a wrapper
element. `tokens.css` keeps only the Sentosa defaults (which remain correct if the
injection hasn't happened yet):

```css
/* tokens.css — Sentosa is the default venue; values are overridden at runtime */
:root {
  --scene-sky: #5fb8ec;
  --sea:       #2f7dd1;
  /* … */
}
```

At runtime, when the venue changes, `GameboyShell.tsx` reads `getVenue(id).tokens` and
writes them to `document.documentElement.style`. `gameboy.css` continues to reference
`var(--scene-sky)` etc. unchanged.

### 3.10 CSS animations — reducing Sentosa coupling

The `prefers-reduced-motion` hide rule in `gameboy.css` currently names `cablecar`,
`express`, and `ferry` explicitly. Each venue contributes a list of "things that travel"
(class tokens that should be hidden, not frozen). This list is data, not hardcoded CSS.

Approach: generate a small inline `<style>` block in the scene component that adds the
venue-specific hidden-under-reduced-motion rule, instead of having it in the static
stylesheet. The static sheet keeps the fallback for the Sentosa classes so SSR and
no-JS cases are not regressed.

Alternatively (simpler): keep the Sentosa classes in the static sheet and add new
venue classes there when they are created — acceptable since the CSS is already
enumerated per ADR-022 and adding a line per new venue is low cost.

### 3.11 Lazy loading

The real scene is 18 MB of photographs. The pixel scenes are tiny (< 50 kB total).
No real venue art should be in the initial JS bundle.

Approach: `import('../../lib/scene/venues/sentosa/realArt.js')` is a dynamic import
inside `RealBeachScene.tsx`. For the initial render a skeleton is shown. The registry
holds the pixel art as static imports (tiny) and the real art as async factories.

For the pixel art, the current approach (all in the initial bundle) is fine — each
venue's pixel art module is small.

## 5. Tests to add

### 5.1 `lib/scene/venueRegistry.test.ts` (new — Stage 2)

describe('venue registry', () => {
  it('contains at least one venue', () => {
    expect(listVenues().length).toBeGreaterThan(0);

## 7. How to add a new venue (checklist)

### 7a. Pixel venue (classic + fine)

- [ ] Write `apps/web/scripts/venues/<id>/pixel-art.mjs` — drawing code for the new
      panorama. Follow `scripts/venues/sentosa/pixel-art.mjs` as the template. Export
      `drawPanorama(scale)` with the same contract.
- [ ] Write `apps/web/scripts/venues/<id>/pixel-sprites.mjs` — sprites for the moving
      parts. Layer set and names do NOT have to match Sentosa's; name them for what they
      are at this venue.
- [ ] Write `apps/web/scripts/venues/<id>/generate-pixel.mjs`. Run it:
      `node apps/web/scripts/venues/<id>/generate-pixel.mjs`. This writes:
      - `public/venues/<id>/pixel/*.png`
      - `public/venues/<id>/pixel-2x/*.png`
      - `apps/web/src/lib/scene/venues/<id>/pixelArt.ts`
- [ ] Write `apps/web/src/lib/scene/venues/<id>/definition.ts`. Start with
      `styles: ['classic', 'fine']` and `real: null`.
- [ ] Register the venue in `lib/scene/venueRegistry.ts`.
- [ ] Confirm the registry contract test passes.
- [ ] Add `data-testid="beach-scene"` assertion for the new venue's layer count in a
      new test file `components/participant/<VenueName>Scene.test.tsx`.
- [ ] Write an ADR entry documenting the venue.

### 7b. Real (photoreal) venue

- [ ] Prepare source photos in `.scene-src-<id>/` or a venue-specific source directory.
- [ ] Write `apps/web/scripts/venues/<id>/generate-real.mjs` (image processing pipeline).
      Follow `scripts/venues/sentosa/generate-real.mjs`.
- [ ] Write `apps/web/scripts/venues/<id>/real-geometry.mjs` — sprite sizes and
      positions for the venue's layers.
- [ ] Run the generator. Output: `public/venues/<id>/real/*`,
      `apps/web/src/lib/scene/venues/<id>/realArt.ts`.
- [ ] Update the venue's `definition.ts` to set `real:` and add `'real'` to `styles`.
- [ ] Confirm `RealBeachScene.test.tsx` equivalents pass for the new venue.

### 7c. CSS for a new venue's travelling layers

- [ ] Identify which layers travel (animate across the scene).
- [ ] Add their CSS class tokens (`gb-scene__<name>`) to the
      `prefers-reduced-motion` hide rule in `gameboy.css`, OR use the dynamic
      injection approach from §3.10 so the stylesheet stays venue-agnostic.

## 8. Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| Stage 1 body move breaks the generators' relative import paths | Medium | Run generators immediately after move; CI catches broken output |
| `?v=` cache-bust hash changes in Stage 3 (asset path change) → stale service worker | Medium | The service worker (ADR-156) uses versioned URLs; old URLs simply miss cache, and fresh assets are fetched |
| New venue's CSS token names conflict with Sentosa-specific ones (`--merlion`) | Low | `VenueTokens` interface only includes the structural tokens; venue-specific decorative colours (like `--merlion`) are not part of the contract |
| Real scene lazy loading adds a flash of empty content on first `?backdrop=real` | Medium | Show the pixel scene as placeholder while the real art loads; this is a style decision, not a blocker |
| Superadmin venue change propagates slowly (polling interval) | Low | Same trade-off as every other config change; document expected propagation time |
| Tournament overhaul leaves a participant code change that conflicts with Stage 4 | Medium | Resolve in the same PR; `BeachScene.tsx` and `GameboyShell.tsx` are the only shared touch points |
| `merlion` motif name is Sentosa-specific — motif inventory is not yet venue-scoped | Low | Motifs are decorative and are used independently of which scene is showing; leave them for a separate plan |
