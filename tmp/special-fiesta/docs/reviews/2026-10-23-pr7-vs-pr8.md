# PR 7 vs PR 8: the two repo points, and what the distance between them costs

- **Date:** 2026-10-23
- **The two repo points, identified:**
  - **PR 7** — head `240519b` (`arena/4ca3593f-special-fiesta`), *"Nine-team day: a named tournament shape, a 13:30 first match, and the setup that offers both (ADR-311)"*. One commit sitting directly on `a5585b1` (ADR-310, the stage pipeline). Declared base: PR 6 (`arena/1952d326-special-fiesta`).
  - **PR 8** — head `d91dceb` (`arena/b49bbc5d-special-fiesta`), *"One-way switch to court awards, and team-level point attribution (ADR-336/337)"*. Declared base: `main`. Its own work is 15 commits (+10,885/−2,062 across 87 files) on top of PR 6's tip `a6dff61` (ADR-335), which itself is 36 commits past ADR-310.
- **The difference between the points:** `git diff 240519b d91dceb` = **278 files, +27,571/−3,875**. In one direction it is the whole switch era (ADR-336 phases 1–4, ADR-337 attribution, ADR-338 pause, ADR-339 drain, ADR-340 ask, ADR-341 predecessor rule, ADR-342, the browser walk, the size loop, a GREENFIELD assessment doc); in the other it is the nine-team day (18 files, +811/−32), which PR 8's lineage does not contain.
- **Focus:** weaknesses, as asked. Strengths are acknowledged only where the weakness is their shadow.

---

## 1. The register is colliding, and nothing detects it

The single worst finding, and it is structural rather than anyone's single mistake:

- **PR 7's ADR-311 is "the nine-team day."** PR 6/PR 8's register has **ADR-311 as "the stage builder: the pipeline reaches the desk and the rehearsal"** (line 11385 at PR 8's head). Two different decisions carry the same number on two branches that both claim to descend from the same register.
- It does not stop there: **PR 8's ADR-342 is "the switch is terminal"** (line 12140 at its head), while the sibling branch `arena/07ce096c-special-fiesta` carries **ADR-342 as "the ask never expires"** — a third collision, on the same day, in the same file. (This reviewer's own branch is one of the colliders; recorded here because a weakness review that hides its own instance is not a review.)
- **Why it happens:** the register is append-only and numbering is "next integer after the last entry **on my branch**." Two branches diverging from ADR-310 both allocate ADR-311. Nothing in the repo — not `check-standards`, not CI, not the register's own format rules — notices a collision until merge.
- **Why it is expensive:** the register's whole value is that a number is a stable pointer (ADR-139: "a name that moved is a dangling pointer"). A collided number is worse than a moved name: both entries look legitimate, grep finds both, and fixing it after merge requires renumbering one chain and rewriting every cross-reference to it — through supersession rows, plan documents, and code comments (`packages/tournament/src/scheduler/presets.ts` cites "ADR-311" in four places on PR 7's side).
- **The textual symptom is already visible:** `git merge-tree` of PR 7 into its declared base's current tip conflicts in **five files**, and `docs/addenda/ADDENDA.md` is one of them — both branches appended a different block right after ADR-310.

**Recommendation.** A `check-standards` rule that parses `^### ADR-(\d+)` and fails on a duplicate number, plus a merge-order convention (the register renumbers on rebase, before review, not after merge). Cheap, and it would have caught both collisions at commit time.

## 2. PR 7: the base moved 36 commits under it, and the PR hides that

- PR 7's actual parent is `a5585b1` (ADR-310). Its **declared base branch** (PR 6) has since advanced to `a6dff61` — 36 commits carrying ADR-311–335 (day-of lock-ins, the rebuild-stage work, the size loop, ADR-324's process hardening).
- GitHub's "Files changed" tab shows a clean 18-file diff, because it is a three-dot diff against the merge base — **it does not show that the PR cannot merge into its own base**. A trial merge (`git merge-tree a6dff61 240519b`) conflicts in **`schema.sql`, `apps/web/src/lib/api/tournament.ts`, `useTournamentSetup.ts`, `SetupPanel.tsx`, and `ADDENDA.md`** — every one of PR 7's central files was also touched by the base's drift (`contracts/tournament.ts` 9 times, `schema.sql` 5, `useTournamentSetup.ts` 5, `SetupPanel.tsx` 4).
- The PR body's own gate notes quietly reveal the drift's cost: it reports bootstrap memory exhaustion and `tmp/Kallang` lint red "on PR #6's head as well" — i.e. the PR was validated against a base state that no longer matches its parent.

**Assessment.** Stacked PRs are legitimate, but an un-rebased stack whose Files-changed tab looks mergeable is a trap: the reviewer approves an 18-file diff and the merge produces five conflicts in files the reviewer never saw diverge. **Recommendation:** rebase PR 7 onto PR 6's tip (renumbering its ADR per §1) or retarget it at `main` with PR 6's work explicit; and treat "base branch advanced past my parent" as a red CI state, not a footnote.

## 3. PR 8: 3,210 files against `main` — a PR that cannot be reviewed

- PR 8's diff against its declared base `main` is **3,210 files, +244,019 lines** — because the branch was fast-forwarded onto PR 6's tip, and PR 6's own lineage carries the ADR-176–335 era. The PR body admits this in a "Base note," which is honest, but honesty does not make a 3,210-file diff reviewable.
- The PR's *own* decision content is excellent and compact (ADR-337 built; ADR-336 planned) — and it is invisible. A reviewer cannot tell, from the diff, which of the 87 files are PR 8's work and which are three other PRs' work riding along.
- The merge-order coupling is total: merging PR 6 first would shrink PR 8's diff by ~3,100 files and change its shape entirely; merging PR 8 first would close PR 6 by side effect. Nothing in either PR states the intended order.

**Assessment.** Same class of weakness as §2, mirrored: PR 7 is too far *behind* its base, PR 8 is far *ahead* of it. **Recommendation:** PR 8 should be retargeted to `arena/1952d326-special-fiesta` (PR 6) so its diff is its own 87 files, with a merge-order note; the fast-forward-onto-`main` presentation should be reserved for the final integrating PR.

## 4. Test regimen: strong where the sandbox allowed, and both PRs ship known-red

Both PRs test substantially better than the average repository — real databases, sabotage checks named per behaviour (PR 7: "final length 20→15 fails 7 engine tests"; PR 8: the whole ADR-324 sabotage ledger), sizes and browser walks on PR 8's side. The weaknesses:

- **The two red web tests travel through both PRs unfixed.** `declare-winner.test.tsx` (F23) and `useCourtConsole.test.ts` failed at ADR-334, still fail at PR 7's point, still fail at PR 8's head (no commit in `a6dff61..d91dceb` touches either file), and both PR bodies list them as "pre-existing" and move on. A red suite that is *documented* rather than *fixed* is still a red suite: it masks new failures in the same files, and it teaches contributors that red is a normal state. (Both are being fixed on `arena/07ce096c-special-fiesta`; the point here is that neither PR 7 nor PR 8 did.)
- **PR 7 shipped a UI change with zero browser evidence.** A new Shape select, a new time field, and a new refusal path — and "Not run: the Playwright suite" is the PR's own last line. The repository's own standard (§3 of GREENFIELD; ADR-192's lesson that placement/visibility defects are invisible to jsdom) makes this a gap, honestly stated but not closed. The `chooseShape` defaulting (`13:30` filled only when the field is blank) is exactly the kind of behaviour a real browser run exercises.
- **PR 7's sandbox gaps are broad:** `bootstrap.test.ts` cannot finish (14 of 25 tests unrun at that point), and lint is red in a tracked `tmp/Kallang/` tree — a lint exception that lives *in the repository*, so every future PR inherits it and every PR body has to re-explain it.
- **PR 8's evidence is per-file, not whole-suite:** the body states the whole-API run still hits `ERR_IPC_CHANNEL_CLOSED`, so suites were run individually. Stated plainly (good), but "147 passed" is 16 separate processes' worth of green, not one — cross-suite interference (the thing ADR-192 diagnosed) is unmeasured at that head by construction.

## 5. Code quality: the diffs are good; the weaknesses are at the edges

- **PR 7** is a tight, well-factored change: `NINE_TEAM_DAY` as the one source the form, API tests and engine tests all read; `planningFloor` as a pure exported function; the schema change additive and nullable with the `ADD COLUMN IF NOT EXISTS` repeated for existing databases (exactly ADR-168's rule). Edge weaknesses:
  - **`SHAPE_LINES` can lie.** The Start form renders three static description lines — `"...a 13:30 first match, a 15:00 hard stop"` — directly beside editable *First match* and *Hard stop* fields. An operator who sets 14:00 sees the form insist on 13:30. The lines derive pool/final durations from `NINE_TEAM_DAY` (good) but hardcode the two times the operator can change.
  - **The shape is a slot, not a parameter.** `nineTeamDayProblem` refuses any count but exactly 9; a "ten-team day" request means a second named preset, parallel constants, and a second problem function. The pipeline machinery underneath is general — the preset layer chose a new slot per day-shape, the pattern ADR-198 warned about in another domain ("variety as a roster, not as more slots").
  - `SetupPanel.tsx` reaches 800+ lines of `FormatChoice`/`ShapeChoice`/`TimingFields`/`FormatOptions` fragments — within the `.tsx` cap, but the file is one more shape away from the same pressure that produced it.
- **PR 8** (its own 15 commits) carries the harder code — pause precedence in the core, per-court drain, transactional three-writer day rows, numeric point-slicing with the six-decimal collapse centralised in the leaderboard SQL (`leaderboard.ts:193`) and rounding centralised in `format.ts`. Edge weaknesses:
  - **Playwright config proliferation.** `playwright.mode-switch.config.ts` is the **third** bespoke config (besides the main config and `playwright.full-event.config.ts`), and each duplicates the `PSD_E2E_CHROMIUM` + launch-flags stanza and hardcodes its own ports and scratch dirs. ADR-170 already paid for this class of drift once (`dirname` joins counting one directory too few, caught only by `--list`); the executable-path stanza is one more thing three files must remember identically.
  - **Plan-doc churn is visible in the commit trail.** ADR-332's reversible switch is planned, then ADR-336 revises it one-way; ADR-340's expiring ask is built, then (on the sibling branch) reversed. Each reversal is handled correctly by the supersession machinery — and each costs register rows, supersession entries, and reader trust. The pattern: recording *plans* as numbered decisions before the desk work validates them. The register's own discipline (decide, then record in the same change) is being bent toward "record the intention, supersede it next week."

## 6. Documentation standard: the highest-quality dimension, with two systematic gaps

Both PRs document far above the norm — every change has its ADR written in the same commit; PR 7's entry carries a **Caveats** section that names what was *not* run; PR 8's body separates "built" from "planned" and states sandbox limits plainly. The gaps:

1. **The register's append-only numbering has no collision guard** (§1) — the documentation system's own integrity rule is unenforced at exactly the point where parallel branches stress it.
2. **PR descriptions are the only place merge-order and base-drift facts live**, and they drift themselves (PR 7's body discusses PR 6's head state that its parent does not contain). A stacked-PR repository needs the stack order in a file the CI can read, not in prose that goes stale between the PR's opening and its review.
